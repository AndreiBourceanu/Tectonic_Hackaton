# Trust Lens

Trust Lens is the bridge between the customer organisation's search engine/AI and it's users. 

Answers with visible trust. For every question, Trust Lens finds the relevant company documents (through the organisation's own search engine/AI agent), scores each one on **freshness, ownership, applicability and agreement**, and tells you whether you can rely on the answer, should check first, or should not act yet. It surfaces conflicts between sources, flags knowledge gaps, and names who to ask.

The demo uses a fictional company ("Northwind") with 11 documents and three payroll questions. No real data is used.

## Quick start

```bash
npm start            # UI + API at http://localhost:3000  (Node >= 18, no dependencies)
npm test             # 23 tests (node:test)
npm run demo         # scripted CLI demo: good case / conflict case / gap case
```

Optional: `PORT=8080` changes the port, `TRUST_NOW=2026-09` changes the reference date used for freshness.

## How everything works

### 1. The big picture

```
data/corpus/*.md ──► src/ingest.js ──► src/trust.js ──► src/server.js ──► public/index.html
 (source files)      (parse + link)    (score + verdict)   (HTTP API)        (UI)
 data/questions.json ─┘                                        │
                                                               └─► in-memory gap log
```

1. **Corpus:** the organisation's documents live as files in `data/corpus/`.
2. **Ingestion** reads every file, extracts its metadata, and links it to the question it answers.
3. **Scoring** ranks the sources for one question and one country and decides the verdict.
4. **Server** exposes the result as JSON and serves the UI.
5. **UI** calls the API and shows the verdict, conflicts, who to ask, and the source files.

### 2. The corpus (`data/corpus/`)

Each simulated file is Markdown with a small header (front matter - hypothetically generated by the organisation's AI):

```
---
title: Payroll Manual v7
type: Policy                       # Policy, Chat, Wiki, Email, Contract...
date: 2026-03                      # last update, YYYY-MM
owner: Nadia Peeters (Payroll BE)  # empty = nobody is accountable
countries: BE                      # where it applies, comma separated
topic: leaver-bonus                # which question it answers (omit = ignored)
claim: A                           # documents with the same claim agree
answer: Pro rata by months worked  # the statement the document makes
---
(the actual document text)
```

The files contain planted problems on purpose: a stale wiki page, an ownerless chat that contradicts the official manual, a forwarded email of unknown origin, and a country (Germany) with no coverage for one question. `holiday-policy.md` has no `topic` and shows that unrelated files are ignored.

`claim` and `answer` are written by hand here. For real documents, an LLM extraction step would fill these two fields (see "Extending" below).

### 3. Ingestion (`src/ingest.js`)

`load()` reads all `.md` files, parses the header and body, validates required fields (a file with a `topic` must also have `claim` and `answer`), then attaches each document to the question with the matching id from `data/questions.json`. Each question also carries the `expert` to contact when the documents are not enough.

### 4. Scoring (`src/trust.js`)

This is pure logic with no I/O. For a given question and employee country, every source gets up to 100 points:

| Dimension | Points | Rule |
|---|---|---|
| **Fresh** | 30 / 20 / 10 / 0 | updated ≤ 6 / ≤ 18 / ≤ 36 / more than 36 months ago |
| **Owner** | 20 or 0 | a named owner exists (someone is accountable) |
| **Applies** | 30 or 0 | the source covers the employee's country |
| **Agreed** | 0 to 20 | +10 for each *other applicable* source with the same `claim` (max 20) |

Sources that do not apply to the country are still shown (greyed out) but are never used as the answer, and they earn no "Agreed" points.

**Verdict** (computed from the best applicable source):

| Verdict | Condition |
|---|---|
| 🟢 **You can rely on it** | top score ≥ 75 **and** no conflict |
| 🟡 **Check before you act** | top score ≥ 50, or there is a conflict |
| 🔴 **Don’t act on this yet** | top score < 50, or no source covers this country (a knowledge gap) |

A **conflict** exists when the applicable sources contain more than one distinct `claim`. The UI then shows the two competing statements side by side. The "Who can help" box appears whenever the verdict is not green. If no source covers the country, it says no expert is mapped and suggests escalating and documenting the answer.

The scoring weights and thresholds are constants at the top of the functions, so they are easy to tune.

### 5. The API (`src/server.js`)

A plain Node `http` server with no framework.

| Method | Path | Purpose |
|---|---|---|
| GET | `/` | serves the UI |
| GET | `/api/health` | liveness and the demo date |
| GET | `/api/questions` | questions, countries, score maxima |
| POST | `/api/answer` | body `{questionId, country}`. Returns verdict, answer, conflict, expert and all sources with per-dimension scores, explanations and the source `file` |
| GET | `/api/documents` | list of corpus files (metadata only) |
| GET | `/api/documents/:file` | full text of one source file |
| GET | `/api/gaps` | ranked log of questions that were not fully reliable |

Invalid input (unknown question, unknown country, broken JSON, body over 10 KB) returns `400` with an `error` message. Unknown routes return `404`. The document route only serves files that were ingested, so paths like `../package.json` are rejected.

The **gap log** is kept in memory. Every answer that is not green is recorded, and `/api/gaps` ranks the most frequently asked unreliable questions. This turns the tool into a feedback loop for improving the knowledge base, and it resets when the server restarts.

```bash
curl -s localhost:3000/api/answer -H 'Content-Type: application/json' \
  -d '{"questionId":"leaver-bonus","country":"BE"}'
```

### 6. The UI (`public/index.html`)

A single page with no build step. It loads the questions from the API, then on every change of question or country calls `POST /api/answer` and renders the result:

- the verdict card (colour, answer, based-on source and score, conflict banner, who can help);
- the ranked sources, each with four tappable score bars that show *why* (freshness, owner, applicability, agreement);
- an **Open source file** button that fetches and shows the original document text.

All text coming from the API is HTML-escaped. If the backend is unreachable, the page shows an error banner instead of breaking.

### 7. Walking through the three demo scenarios

| Scenario | Result | Why |
|---|---|---|
| Retro correction, **NL** | 🟢 rely | Approval matrix scores 80 (fresh, owned, applies, confirmed by the wiki) and nothing contradicts it. The chat only covers BE. |
| Leaver bonus, **BE** | 🟡 check | The manual scores 90, but an ownerless chat says something different, so the conflict caps the verdict. The chat is named as the contradiction and Nadia Peeters is suggested. |
| Leaver bonus, **DE** | 🔴 don't act | No source covers Germany. It is reported as a knowledge gap and logged. |

Run `npm run demo` to see these in the terminal, including the score breakdown per source and the gap log.

### 8. Tests (`test/`)

- `trust.test.js`: freshness buckets, agreement cap, applicability, conflict handling, gap handling, each verdict.
- `ingest.test.js`: front matter parsing, validation errors, corpus loading (11 files, 10 linked, distractor ignored).
- `api.test.js`: every endpoint, input validation, 404s, path-traversal protection, gap logging.

## Extending

- **Add a document:** drop a `.md` file with the header above into `data/corpus/`. Restart the server.
- **Add a question:** add an entry (`id`, `text`, `expert`) to `data/questions.json`, then tag documents with that `topic`.
- **Add a country:** add it to `COUNTRIES` in `src/trust.js` and to the dropdown in `public/index.html`.
- **Real documents:** replace the hand-written `claim` and `answer` fields with an LLM extraction step in `src/ingest.js`. It would read the document body, return the statement it makes for a topic, and group equivalent statements under the same claim. Conflict detection, scoring and the UI then work unchanged.

## Limitations (proof of concept)

- The corpus is fictional, small and loaded once at startup.
- Claims are labelled by hand, so conflict detection is only as good as those labels.
- Scores are simple, transparent heuristics and not calibrated against real-world outcomes.
- The gap log is in memory only and there is no authentication.
